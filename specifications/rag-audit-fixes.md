# Задание: исправление критических дефектов RAG MCP Tool

> **Адресат:** следующей LLM, которая будет править код RAG MCP Tool.
>
> **Источник проблемы:** тщательный аудит через MCP-интерфейс самой RAG на существующих данных (42 документа в `list_documents`, граф 117 узлов / 130 рёбер, 23 типа реляций). Все находки воспроизводимы через MCP-вызовы без доступа к ФС.

---

## Контекст и методология аудита

Аудит проводился исключительно через MCP-инструменты RAG (без чтения файлов): `rag_search`, `rag_bm25_search`, `rag_search_hybrid` (alpha 0 / 0.2 / 0.5 / 0.8 / 1.0), `rag_get_related` (max_depth 1–2), `rag_get_document` (с пагинацией), `rag_list_documents`, `rag_stats`, `rag_graph_stats`. Использованы реальные запросы трёх типов: (1) английские с ключевыми терминами (`orchestrator dispatches events`, `JWT token issuance authentication`), (2) русские концептуальные (`хранилище решений и находок проекта`), (3) технические (`docker deployment`). Результаты сверялись с содержимым документов через `rag_get_document`.

---

```
rag_bm25_search("the", k=100)     → 30+ документов, отсутствующих в list_documents
rag_get_document("04fe4bec-...")  → null
rag_bm25_search("orchestrator")   → находит 04fe4bec, 217ab1a9, ca54b2b0 (score ~10)
```

**Контрактное нарушение:** документ, который возвращает поиск, обязан быть читаемым через `get_document`. Сейчас это не так.

**Ожидаемое поведение:** единый реестр документов. Все три стора (vector, BM25, graph) индексируют ОДИН И ТОТ ЖЕ набор doc_id. `list_documents`, `get_document`, `delete_document`, `rag_search*` работают с одним и тем же пространством идентификаторов.

**Где искать в коде:**
- `src/mcp_server.py` — где `rag_add_document`/`rag_add_file` writes расходятся по сторам
- `src/bm25_index.py` — персистентность BM25 (см. `specifications/bm25_persistence_fix.md`)
- `src/vector_store.py` (ChromaDB) — возможно, отстают индексации
- `rag_data/` — три отдельных файла/директории, которые не синхронизируются атомарно

**Требование:** провести рехеширование всех трёх сторов из единого источника истины. Возможно, потребуется intro/replay механизм: при запуске сверить множества doc_id в vector/BM25/graph и автоматически реиндексировать отстающие. Альтернатива — WAL (write-ahead log) с транзакционной записью во все сторы.

### D2. «Фантомные» узлы в графе

**Симптом.** `rag_graph_stats` показывает 117 узлов при 42 документах. `rag_get_related("04fe4bec-...")` возвращает рёбра на узлы `c2c69883`, `9703e2dd`, `ad1b7f0c` — этих doc_id нет ни в vector, ни в BM25, ни в `get_document`.

**Воспроизведение:**
```
rag_get_related("04fe4bec-9260-472e-95ac-47674537d2c3", max_depth=1)
→ edges to c2c69883, 9703e2dd, ad1b7f0c (несуществующие)
```

**Ожидаемое поведение:** граф содержит ТОЛЬКО узлы, backed реальными документами. Если документ удалён — его узел и все инцидентные рёбра удаляются.

**Требование:** при `rag_delete_document` каскадно удалять узел графа и все рёбра (in/out). При загрузке графа валидировать, что каждый node_id существует в реестре документов; отсутствующие — отбрасывать с предупреждением.

---

### D3. `rag_get_related` следует только исходящим рёбрам

**Симптом.** Для Auth Issuer (`af029163-561e-4893-ba03-b6520a53d006`) `get_related` возвращает `{relations: []}` — пусто. Однако существует ребро `7cb4547e → uses → af029163` (Journal Service использует Auth Issuer). Узлы-«приёмники» выглядят изолированными.

**Воспроизведение:**
```
rag_get_related("af029163-...", max_depth=2)   → пусто
# но есть ребро 7cb4547e →uses→ af029163, найденное через get_related("7cb4547e")
```

**Ожидаемое поведение:** BFS должен обходить рёбра в ОБА направления (out + in). Опционально — параметр `direction: "out" | "in" | "both"` (по умолчанию `"both"`).

**Требование:** в `rag_get_related` добавить реверсивный обход; при сохранении направления в ответе помечать его (например, поле `direction` в каждом элементе `relations`).

## Серьёзные дефекты (портят качество поиска)

### D4. Семантический поиск проваливает русские концептуальные запросы

**Симптом.** Запрос «хранилище решений и находок проекта» — это прямое описание Journal Service (`7cb4547e-c2fa-4044-a294-5df645dd58e4`). `rag_search` его НЕ находит; топ-выдача: RAG MCP Tool, Architecture Revisions, CHANGELOG, rnd-agents — нерелевантный мусор. Аналогично «orchestrator dispatches events» не находит Orchestrator (`2dd2afe0`), хотя BM25 находит мгновенно со score 10.16.

**Симптом-2 (скоры):** для русских запросов скоры кластеризованы в узком диапазоне 0.32–0.55, дискриминация между релевантными и нерелевантными документами почти нулевая. Группа PROGRESS-документов (20+ шт.) имеет скор 0.332x–0.334x — то есть все «одинаково нерелевантны».

**Ожидаемое поведение:** концептуальный русский запрос должен находить документ, описывающий именно эту концепцию, в топ-3.

**Требование:** заменить эмбеддинг-модель на multilingual (например, `multilingual-e5-large` или `bge-m3`). Текущая модель (4096-dim, вероятно англо-центричная, OpenRouter-based) неприменима для русского корпуса. Если замена невозможна — по умолчанию поднимать вес BM25 в hybrid (`alpha=0.3` вместо 0.5) и документировать ограничение.

---

### D5. Короткие «мусорные» документы лидируют в семантической выдаче

**Симптом.** На запросе JWT при `alpha=0.8` документ `c1941e5a` («full check: json string meta», 5 слов) обходит Auth Issuer (score 0.80 vs 0.20). Четыре regression-обрывка загрязняют выдачу:

- `0d4985b7` — «full check: empty string meta»
- `3643812b` — «full check: null meta»
- `c9d5a1ec` — «full check: dict meta»
- `c1941e5a` — «full check: json string meta»

**Ожидаемое поведение:** короткие обрывки (< 50 символов или без смыслового содержания) не должны ранжироваться выше полноценных документов.

**Требование (двухчастное):**
1. **Очистка корпуса:** удалить 4 «full check» документа через `rag_delete_document`. Это регрессионные тестовые обрывки, не несущие ценности.
2. **Защита от повторного появления:** в `rag_add_document` добавить опцию `min_content_length` (по умолчанию 50 символов) — документы короче порога отклоняются с предупреждением. Опционально — штраф за длину в ранжировании (length normalization) либо фильтр «title-only» документов.

---

### D6. Дубликаты документов не детектируются

**Симптом.** `8006097e-524b-480a-a6dd-46c1277b1bfa` и `45b48706-2d8b-4609-ad4a-b92d81514b33` — почти идентичные копии RAG MCP Tool; оба в выдаче одновременно (видно в `rag_search("agent")` и в запросах по RAG).

**Ожидаемое поведение:** при добавлении документа с дублирующим содержимым либо отклонять, либо обновлять существующий, либо помечать как версию.

**Требование:** в `rag_add_document` вычислять хэш нормализованного контента (lowercased + stripped + whitespace-collapsed). Если хэш совпадает с существующим — возвращать `existing_doc_id` с флагом `duplicate=true` (по умолчанию), и опцией `force_new=true` для явного создания версии.

---

### D7. Нормализация hybrid даёт тай-оффы

**Симптом.** При `alpha=0.5` на запросе «orchestrator dispatches events» топ-2 результата имеют одинаковый score 0.5 — ранжирование теряет смысл. Формула `alpha * semantic + (1-alpha) * bm25` после min-max нормализации склеивает скоры.

**Воспроизведение:**
```
rag_search_hybrid("orchestrator dispatches events", alpha=0.5, k=5)
→ 04fe4bec (score 0.5), 67307c9c (score 0.5) — тай-офф
```

**Ожидаемое поведение:** строгий порядок ранжирования без вырожденных тай-оффов.

**Требование:** пересмотреть формулу. Рекомендация — Reciprocal Rank Fusion (RRF) вместо линейной комбинации: `score = 1/(k+rank_sem) + 1/(k+rank_bm25)` (k=60 — классика). RRF устойчив к разным шкалам и не требует нормализации. Опционально сохранить `alpha` как вес между рангами. Документировать новый формат score, так как он перестанёт быть в [0,1].

## Менее критичные замечания

### D8. Граф разрежен для PROGRESS-документов

Journal Service (`7cb4547e`) имеет всего 1 ребро (`uses → Auth Issuer`). Между агентами-«стражами» (Architecture Guardian, Code Guardian, Tests Agent, Tasks Guardian, Wiki Guardian) и их сервисами связей почти нет. Auth Issuer как центр авторизации не связан с потребителями (из-за D3 — направленности рёбер).

**Требование:** после исправления D3 (двунаправленный обход) многие «разрывы» исчезнут. Дополнительно — при индексации спецификаций автоматически выводить рёбра из явных ссылок (`uses`, `depends_on`, `connects_to`) в тексте.

### D9. BM25 не фильтрует английские стоп-слова

На запросе `bm25_search("the", k=100)` ранжирование отличается от случайного только за счёт IDF «the» во всех документах — фактически шум. Релевантные и нерелевантные документы разделены скорами 2.40–2.48 (узкая полоса).

**Требование:** добавить стандартный список английских стоп-слов (NLTK + custom). Для русского корпуса — отдельный список. Опция `remove_stopwords: bool` (по умолчанию `true`) в токенизации BM25.

### D10. Метаданные эхом возвращаются корректно, но нормализация inconsistent

В `list_documents` метаданные отображаются как `{}` для документов с empty/null meta, но при `search` те же документы возвращают `null`. Это не баг, но создаёт путаницу в клиентском коде.

**Требование:** унифицировать — `metadata` всегда словарь (возможно пустой `{}`), никогда `null`.

## Что работает корректно (не трогать)

- **Пагинация `get_document`:** `offset`/`limit`/`total_chars` работают точно. Проверено: `get_document("2dd2afe0-...", limit=200)` → `total_chars=30290`, корректный срез.
- **Метаданные в search-выдачах:** эхо-возвращение метаданных во всех трёх search-методах работает.
- **BM25 для точных терминов:** score 7–10 для JWT/orchestrator — высокая точность.
- **Граничные случаи:** `get_document(несуществующий_id)` → `null` без исключения; `k=100` при 42 документах → возвращает 42 (без падения/ошибки).
- **Веса рёбер графа:** осмысленны (0.7–1.0), типы реляций логичны (`dispatches_to`, `runs_on`, `uses`, `serves`, `monitors`).
- **`alpha=0.2` — рабочий sweet spot:** для запросов с ключевыми терминами гибрид с перевесом BM25 даёт лучшее разделение; semantic добавляет полноту.

## Тесты приёмки (определение «готово»)

После внедрения выполнить через MCP (без ФС) и убедиться:

1. **D1:** `rag_list_documents(limit=1000)` возвращает столько же документов, сколько уникальных doc_id в `rag_bm25_search("<common_term>", k=1000)`. Любой doc_id из `rag_search*` читается через `rag_get_document`.
2. **D2:** `rag_graph_stats().total_nodes == rag_list_documents(limit=1000).total`. `rag_get_related` не возвращает рёбер на несуществующие doc_id.
3. **D3:** `rag_get_related("af029163-...", max_depth=1)` возвращает непустой список, включающий Journal Service.
4. **D4:** `rag_search("хранилище решений и находок проекта", k=3)` возвращает Journal Service (`7cb4547e`) в топ-3.
5. **D5:** ни один из «full check» doc_id не возвращается ни одним search-методом.
6. **D6:** попытка добавить дубликат RAG MCP Tool возвращает `duplicate=true` и `existing_doc_id`.
7. **D7:** `rag_search_hybrid("orchestrator dispatches events", alpha=0.5, k=5)` не содержит тай-оффов в топ-3 (все скоры различны).
